Eidolon Adaptive Workspace Architecture

Domänenagnostische, need-driven Workspaces statt hardcodierter Hubs. Nutzerpräferenzen und wiederkehrende Themen erzeugen adaptive Arbeitsbereiche — mit harter Core-Shell-Sperre, lokalem Fallback und Feature-Flag-Kill-Switch.

CORE SHELL LOCKED · WORKSPACE HOST SANDBOXED · NEED-DRIVEN GENERATION

Systemfluss

Locked Core Shell

Navigation, Chat, Dashboard, Mesh, Settings, Topbar, Status
  • niemals durch adaptive Module ersetzt
  • bleibt bei Modulfehlern immer bedienbar
  • Fallback bleibt im Core-System renderbar
↓

User Model Store

  • user_model.json
  • Sprache, Visualisierungsstil, Autonomiegrad, UI-Dichte
  • Core-Shell-Lock-Präferenz
↓

Topic Attention Store

  • interaction_log.jsonl + topic_attention.json
  • Wiederholung, Frische, Handlungsrelevanz
  • Need-Scores: planning / tracking / decision / knowledge / execution / reflection
↓

Workspace Generator

  • kein Training-/Health-/Career-Sonderfall
  • Topic + Need + User Profile → Layout + Module
  • Templates: hybrid / planner / tracker / decision / knowledge / review
↓

Workspace Registry

  • workspaces.json
  • Feature-Flag, activate/suspend, aktuelle Themenlage
  • veraltete Vorschläge werden verworfen
↓

Adaptive Workspace Host

  • einziger erlaubter Render-Slot: #adaptive-workspace-host
  • lokale Error Boundary + geschützter Fallback
  • zeigt User Model, Topic Attention und generierte Workspaces

Safety Contract

  • CORE_LOCKED_AREAS schützt Root-Navigation, Chat, Dashboard, Settings
  • safe_mode = "sandboxed"
  • mutable_core_areas = []
  • Fehler im Host führen zu lokalem Fallback statt globalem Script-Absturz

API Surface

  • GET/POST /user/model
  • GET /user/topics
  • POST /user/topics/recompute
  • GET /workspaces
  • POST /workspaces/propose
  • POST /workspaces/feature-flag
  • POST /workspaces/{id}/activate
  • POST /workspaces/{id}/suspend

Current Foundation Scope

  • implementiert: sichere Infrastruktur
  • noch offen: semantische Topic-Clustering-Ebene
  • noch offen: Proactive Assistance Engine
  • noch offen: echte persistente Workspace-Datenmodelle

Warum kein hardcodierter Hub?

Weil das Thema nicht der richtige Primärschlüssel ist — der Unterstützungsbedarf ist es.

Produktlogik

Nicht domain-driven hubs, sondern need-driven workspaces.

Failure Behavior

Workspace kaputt → Host-Fallback. Core Shell bleibt stabil und interaktiv.
